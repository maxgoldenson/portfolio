ESP32 High-Speed Data Logger

A custom PCB built to log over 10,000 sensor samples per second continuously for days — designed from schematic to enclosure to catch the intermittent hardware failures no bench tool can reach.

01 — Problem

The failure only happens when you stop watching

Mechanism failures at Brewbird were intermittent — occurring once every few hundred cycles, under load, after extended operation. A bench oscilloscope can't stay connected for days. Commercial data loggers lacked the right sensor interfaces, sample rate, or were too bulky to fit inside a running machine.

I needed something custom: small enough to install permanently, fast enough to catch transient events, and reliable enough to run for days without intervention. That meant designing a PCB rather than duct-taping dev boards together.

"The failure only happens after 400 cycles. We need something that can watch the whole thing — not just the first five minutes."

02 — Process

Designed for the environment, not the bench

The PCB was designed around three constraints: fit the physical envelope of the machine, survive the electrical environment (motor noise, inductive spikes), and run continuously from a small battery or USB supply without thermal issues.

03 — Solution

Decoupling acquisition from storage

Writing directly to an SD card at 10k samples/sec isn't possible — SPI flash writes have variable latency that will cause sample drops. The solution is to decouple the two operations entirely using a lockless ring buffer in SRAM as an intermediary.

Sensor ISR
Core 0 — highest priority. Hardware timer fires at fixed intervals. ISR reads sensor data and writes a timestamped sample into the head of the ring buffer. Runs at full rate regardless of what Core 1 is doing.
Ring buffer
SRAM — lockless design. Producer (Core 0) and consumer (Core 1) operate on separate head/tail pointers. Buffer depth sized to absorb worst-case SD write latency with margin. Overflow condition triggers a status LED — no silent data loss.
Write task
Core 1 — lower priority. Drains the ring buffer in chunks, packs samples into binary frames with CRC checksums, and writes to MicroSD via SPI. Handles SD card busy-wait without stalling the acquisition core.
Timestamps
64-bit hardware timer. Each sample is tagged with a microsecond timestamp from the ESP32's internal hardware timer — not millis(). Guarantees accurate inter-sample timing even when the write task is under load.
Config
SD card text file. Log rate, active sensor channels, and trigger conditions read from config.txt on boot. No reflashing needed to change deployment parameters — swap the config and power cycle.

The logger directly identified the root cause of several elusive mechanism failures at Brewbird — events that only appeared after hundreds of cycles and disappeared the moment a bench instrument was connected. It's now a standard tool in the hardware debug workflow.

The Python post-processing script decodes binary logs, reconstructs timestamped time series, and plots annotated events — making it easy to share findings with teammates who aren't embedded engineers.

05 — Key Learning

Decouple systems with different timing requirements

The core architectural insight was that acquisition and storage are two fundamentally different operations with incompatible timing constraints, and trying to do them in the same task creates an unsolvable tension. The ring buffer as intermediary is the general solution — decouple the producer from the consumer and let each run at its own rate. This pattern applies anywhere you have a fast real-time source feeding a slow, variable-latency sink.

The second lesson was about the value of custom tooling for intermittent failures. When a bug only appears after 400 cycles under load, the instrument matters as much as the debug process. Commercial solutions weren't designed for this constraint set — building the right tool was faster than adapting the wrong one.
