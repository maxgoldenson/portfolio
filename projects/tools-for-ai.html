Tools-For-AI — Hardware-in-the-Loop Debug Rig

A Raspberry Pi bench node that gives an AI agent real instruments — logic-analyzer capture and decode, signal measurement, ESP32 compile/flash, and serial I/O — exposed as 24 MCP tools. The agent writes firmware, flashes it, measures, and revises until machine-checked pass/fail criteria are met, so every conclusion rests on a real measurement, not the model's own claims.

01 — Problem

AI agents will say firmware works. Hardware disagrees.

An LLM can write plausible embedded firmware all day — but it has no way to know whether the PWM actually comes out at the right frequency, whether the I²C transaction actually ACKs, or whether the board even enumerated. Left unchecked, an agent "verifies" its own code by reading it.

The fix is the same one hardware engineering has always used: don't trust the claim, measure it. That means giving the agent real bench instruments and making a machine-checked measurement — not the model's self-assessment — the only way to pass.

"The agent doesn't get to decide it's done. The logic analyzer decides it's done."

02 — Process

A bench node the agent can actually use

01

Instrument back end on a Raspberry Pi

Built a Python back end on a Raspberry Pi bench node that owns the physical instruments: logic-analyzer capture and protocol decode, signal measurement, ESP32 toolchain compile/flash, and raw serial I/O to the target.

02

24 MCP tools

Exposed every bench capability as typed MCP tools — the agent calls "capture these pins", "flash this build", "measure this signal" the same way it calls any other tool, and gets structured results back instead of screenshots or vibes.

03

Agent loop with an injection boundary

Built the Claude agent loop with an explicit injection boundary: untrusted serial output and compiler text are treated as data, never as instructions. The agent iterates — write, flash, measure, revise — against the real board.

04

Machine-checked pass/fail

Success criteria are evaluated in code against captured measurements, so a run only passes when the hardware behaves — not when the model says it should. A browser Workbench/Assistant app shows runs live, a mock mode enables development without hardware, and 75 automated tests cover the stack.

03 — Solution

An agent that closes the loop on real hardware

The finished rig is a full Python stack: the instrument back end, the Claude agent loop with its injection boundary for untrusted serial and compiler text, and the browser Workbench/Assistant app — with a mock mode for hardware-free development and 75 automated tests keeping it honest.

Hand it a task like "bring up PWM on this pin at 25 kHz" and the agent writes the firmware, compiles and flashes it, captures the pin with the logic analyzer, and keeps revising until the measured waveform meets the machine-checked criteria.

05 — Key Learning

Verification is a tool-design problem

The interesting engineering wasn't prompting — it was deciding what the agent is allowed to trust. Serial output and compiler messages are untrusted input and cross an explicit injection boundary as data; pass/fail lives in code, next to the measurements. Get those boundaries right and the agent's iteration loop looks exactly like a good engineer's: hypothesize, flash, measure, revise.
